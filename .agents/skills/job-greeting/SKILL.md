# Job Greeting

先读仓库根目录的入口规则、`使用说明/workflow.md`、`使用说明/求职内容工作流协议.md` 和 `简历事实库/_index.md`。JD 与截图只在当前对话中处理，不保存文件、截图、匹配报告或索引。

## 选材

1. 从 JD 提取 3～5 个核心要求和硬性门槛，使用 JD 本身的能力语言，不自行扩大要求。
2. 按求职内容工作流协议直接将 JD 与全部 confirmed 事实匹配。
3. 如果同岗位已有 final 简历，先把它作为经过确认的候选范围，再逐条回到事实库核验。不能只压缩现有简历，也不能把简历中的新措辞当成事实。
4. 选择 2～3 个相关性最高、证据最完整的匹配点，尽量来自不同经历。真实匹配不足时只写 1～2 点，不凑数；相关性优先于无关的高指标。
5. 每个匹配点只讲一个子项目或一项具体工作，组合“JD 能力标签＋动作＋结果或产出＋已有指标”。没有结果证据时写到产出为止。
6. 能力标签使用 JD 的语言。confirmed 单位名称只在有助于说明事实出处时作为背书，不能代替能力标签。

## 事实边界

- 只使用 status 为 `confirmed` 的事实。禁止使用 candidate、待确认或冲突事实。
- 禁止虚构经历、指标、工具、年限、单位、职位和任职性质。
- 个人、课程、开源等项目必须保留真实项目性质，不能写成正式任职经历。
- 单位、岗位或事实指代不明确时，在招呼语之外标记待确认，不猜测、不写入正文。

## 输出

固定使用以下结构；只有两个真实匹配点时删去第 3 项，只有一个时继续删去第 2 项，不保留空编号：

```markdown
您好！[与岗位直接相关的背景或开场]，希望有机会进一步沟通。

1. **[JD 能力标签]**：[一个动作＋一个结果或产出＋可用指标]
2. **[JD 能力标签]**：[一个动作＋一个结果或产出＋可用指标]
3. **[可选的第三个匹配点]**
```

从“您好”到最后一个编号匹配点合计不超过 250 个中文字符。保持自然、直接，避免空泛品质宣言、重复项目和无法核实的结论。

硬性门槛缺口放在招呼语正文之外单独提醒，并区分“没有记录”和“明确不满足”。待确认项也放在正文之外，不能先写入招呼语。

结果只在对话中返回。不得创建或更新简历、事实、JD、报告、索引及其他文件。

正式使用只读取 `简历事实库/` 中本人已确认的资料，不读取 `示例资料/` 的虚构事实；事实库为空时先引导用户导入并确认资料。

创建或更新内容时，按 `使用说明/索引规范.md` 同步维护受影响的各层索引与 updated；created 保持不变。正式岗位档案总索引按年份导航，年度索引列具体简历。交付文件实际生成后才增加对应链接。
