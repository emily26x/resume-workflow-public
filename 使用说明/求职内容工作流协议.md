# 求职内容工作流协议

求职 Skill 共用这份协议。简历事实库是唯一内容来源，JD 分析和匹配过程默认不落盘。

## 1. 临时处理 JD

- 文字或图片 JD 只在当前对话中识别、分析和匹配，不创建 `jd.md`、`match.md` 或附件副本。
- 公司或岗位无法识别时向用户确认，不自行猜测。
- 将 JD 拆解为职责、硬性要求、加分项和关键词，提炼 3～5 个核心要求。
- 匹配严格限定在 `简历事实库/`，不从历史定制简历复制或召回内容。
- 只能使用状态为 `confirmed` 的表达。用户提供的新事实须先确认，未经确认不得写入求职材料或事实库。

## 2. 全事实库匹配

依次按以下标准选材：

1. 是否直接满足 JD 硬性要求或核心职责。
2. 工作对象、业务场景和实际动作是否一致或高度相近。
3. 是否有明确结果、产出或交付物。
4. 相关性与事实完整度相当时，优先有可信数字证据的表达。
5. 其他条件相当时，优先更近且事实边界更清晰的经历。

- 不得用弱相关的高指标代替强相关事实。
- 匹配结果区分为“直接匹配”“部分匹配／可迁移”和“缺少证据”。
- 使用 JD 语言重组表达时，不得改变事实对象、行业、合作方或本人贡献边界，不把特定行业术语生硬迁移到其他场景。
- 每条采用的经历必须能回溯到一个或多个 `statement_id`。

## 3. 三类输出

- `job-greeting`：从全库匹配结果中选择 2～3 个最强匹配点，只在对话中返回。
- `interview-introduction`：有同岗位 final 简历时以该简历为优先候选，并回到 confirmed 事实核验；没有时从全库匹配结果中选择两个故事。
- `resume-tailor`：根据 JD 选择相关的 confirmed 经历，决定章节内容、经历组合和表达结构；公共版不设置固定公司组合。

JD 分析、匹配过程、打招呼和自我介绍默认不写入仓库。

## 4. 简历结构与溯源

- 每个现有章节内部的带时间条目按时间倒序排列：进行中优先，其余按结束时间倒序，结束时间相同时按开始时间倒序，无日期条目置底并保持原有顺序。
- 每段入选工作经历固定保留 3 条要点。不足 3 条 confirmed 事实时停止生成，向用户说明证据不足，不得拼接或补造。
- 新建 `resume.md` 不保留已退役的选材字段，在 frontmatter 中用 `source_items` 记录正文实际采用的 `statement_id`。
- `source_items` 只用于内部溯源，不渲染到投递正文、HTML、PDF 或 PNG。

## 5. 保存与交付

- 岗位目录为 `岗位档案/YYYY/YYYY-MM-DD-公司名称-岗位名称/`，草稿阶段只创建 `resume.md`。
- 用户确认后将 Markdown 标记为 `status: final`，在同级生成 `resume.html` 并启动编辑器。HTML 修改不回写 Markdown 或事实库。
- 编辑器根据当前 HTML 生成同级 `resume.pdf` 和 `resume.png`。
- 不保存 `greeting.md`、`self-introduction.md`、`changes.md`、`match.md`、`render.json`、`qa.json` 或 `preview.png`。
- 具体命名、版本、索引和导出规则以 [工作流与公共协议](workflow.md) 为准。
